# ADR 0003: Target Java 21

**Status:** Accepted
**Date:** 2026-01-28
**Authors:** XNAT Core Team
**Deciders:** XNAT Steering Committee

---

## Context

Prior to the monorepo migration, different XNAT modules targeted different Java
versions:

- Most library modules compiled with Java 11 source/target compatibility.
- A few older modules still targeted Java 8.
- The web application (`xnat-web`) had accumulated Java 11 features but was
  never formally declared as requiring Java 11.

XNAT runs on Tomcat, and current Tomcat 10.x distributions ship and officially
support Java 21 LTS.  Java 11 reached end-of-life from most vendors in
September 2023.  Java 17 is available as an interim LTS but is already
approaching EOL from several vendors.

The monorepo consolidation created a natural forcing function: all modules must
agree on a single language level.

---

## Decision

Target **Java 21 LTS** as the minimum compile and runtime Java version for all
modules in the monorepo.

The Gradle toolchain is configured in the root convention plugin to require
`JavaLanguageVersion.of(21)`, which Gradle enforces across all subprojects.

---

## Alternatives Considered

### Java 17 LTS

Java 17 is a mature LTS release with wide ecosystem support.  Targeting Java
17 would have required fewer source-level changes than Java 21.

**Rejected because:** Java 17 is approaching EOL from major vendors (Temurin
17 EOL: October 2027).  Targeting Java 21 now avoids a second upgrade cycle
within the expected lifetime of XNAT 1.10.x.  The incremental source changes
required to move from Java 17 to Java 21 are minor compared to the 11→17 gap.

### Java 11 LTS (status quo)

Continue targeting Java 11 to preserve backward compatibility with deployments
running on older JVMs.

**Rejected because:** Java 11 is end-of-life.  No security updates are
available from most vendors.  Tomcat 10.x requires Java 11 as a minimum but is
optimized for and tested against Java 17 and 21.  XNAT operators running
security-conscious production environments have already migrated to Java 21.

### Dual-compile (Java 11 source, Java 21 runtime)

Compile with `--source 11 --target 11` but run the test suite under Java 21.

**Rejected because:** This approach prevents the use of any Java 11+ language
features or APIs (records, sealed classes, pattern matching, newer NIO APIs)
that can meaningfully simplify the codebase.  It also provides no assurance
that the code actually works on Java 21 since the source level differs.

---

## Implications and Required Changes

The following changes were required to compile and run XNAT under Java 21:

### Removed JDK bundled APIs

Several APIs that were bundled in older JDKs were removed or modularized in
Java 9 through 11.  These are now declared as explicit compile/runtime
dependencies in the platform BOM:

| API | Dependency added |
|-----|-----------------|
| `javax.annotation.*` | `javax.annotation:javax.annotation-api` |
| `javax.inject.*` | `javax.inject:javax.inject` |
| `javax.mail.*` | `com.sun.mail:javax.mail` |
| JAXB (`javax.xml.bind.*`) | `jakarta.xml.bind:jakarta.xml.bind-api` + `org.glassfish.jaxb:jaxb-runtime` |

### Module system boundary enforcement

Java 21 enforces strong encapsulation of JDK internals.  Several places in
`libs/prefs` and `libs/xdat` used reflection to access private JDK fields;
these were refactored to use public APIs.

### Language feature adoption

New Java language features available in Java 21 are available for use in new
code.  The following features are encouraged:

- **Records** for immutable data carriers
- **Sealed classes** for algebraic type hierarchies
- **Pattern matching for `instanceof`** (`if (obj instanceof Foo f)`)
- **Text blocks** for multi-line string literals (SQL, JSON, XML)
- **Switch expressions** with arrow syntax

Existing code is not required to be retroactively updated to use these
features, but new code should prefer them where appropriate.

---

## Consequences

### Positive

- Access to modern Java language features and performance improvements.
- Security patches and long-term support through at least September 2029
  (Temurin 21 LTS EOL).
- Consistent runtime across all modules — no per-module JDK version
  negotiation.
- Gradle toolchain auto-provisioning via Foojay Disco resolver means CI and
  developer environments automatically acquire JDK 21 if not already installed.

### Negative / Accepted Trade-offs

- XNAT deployments on Java 11 or Java 17 will not be supported for 1.10.x
  and later.  Operators must upgrade their JVM.  Release notes and
  installation documentation will be updated to reflect this requirement.
- A small number of source-level changes were required (see above).  These are
  documented in detail in `MIGRATION_REPORT.md`.
